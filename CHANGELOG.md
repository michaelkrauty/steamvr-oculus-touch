# Changelog

All notable user-facing changes are recorded here. Version numbers follow semantic versioning; changes before 1.0 may alter interfaces.

## Unreleased

### Added

- The daemon notices Rift sensors being plugged in and unplugged while it runs, including after it started with none: it checks USB once a second and lets each change settle for a second. An unplugged sensor stops contributing within about two seconds, without interrupting the controllers or reopening the tracking engine. A check of whether it moved, or its placement, ends with it, so another sensor's check does not wait for it. A sensor plugged in while the engine runs is not opened yet: it is used the next time the tracking engine starts, when the daemon restarts or changes tracking mode, and `cv1touch status` and `cv1touch doctor` show it as waiting for that, with the restart command. Doctor and the status board report a connected sensor that is waiting to be opened as waiting, giving the daemon's reason once, not as a cable or bandwidth failure. A wait for a restart or for USB access is reported at once, without asking to run doctor again; one that ends by itself, such as a USB change settling for a second, is checked again. On Linux that reason can be that the USB device is not accessible yet, and on Windows that the driver interfaces are not active yet; if that wait continues, doctor says to run `cv1touch sensors`. A sensor that must be unplugged and plugged back in is reported as its own problem. A sensor whose USB entry is still appearing or leaving is skipped without hiding the others. While the headset is disconnected, status and doctor show the sensors as waiting for it. The hot-plug check does not count that, or an engine opening the sensors, as a sensor failure; doctor still needs advancing video to verify required cameras. Every sensor stream the engine starts is in use until its own device is shown to be gone: by the stream's USB removal error, or by USB scans read after the start that show the sensor gone, or the connection they showed replaced. A replug, removal or USB access change seen while the engine opens is acted on only once the engine's sensors are known, so the daemon neither stops using a sensor the new engine opened nor logs or shows it as waiting. A failed start spends the connection's one attempt only when its identity matches, so an old failure cannot consume a replacement's attempt, even if Linux reuses its USB address; a sensor the engine did not account for waits for the next start, and the log says so, unless USB already shows it unplugged. A failed stream is not retried before the next engine start; after fixing the connection, restart the daemon. Excluded sensors stay closed, saved calibration is reused, and in calibrated mode a new sensor only observes until it has been calibrated. Without saved calibration, startup still uses provisional sensor placement. Closing the engine does not try to reset a sensor whose camera transfers reported it unplugged while open, or warn about it, and does not warn about camera transfers the close itself interrupts.
- The right controller's Oculus button can be bound in SteamVR, game by game, like any other button. SteamVR now shows the controllers as a controller type of their own, Oculus Touch (cv1touch), which uses each game's Oculus Touch bindings until you change one; SteamVR's Oculus Touch type keeps one input profile, its own, which has no place for this button. Nothing is bound to the button by default, and the left Menu button still opens the SteamVR menu. To bind it: in SteamVR, Settings, Controllers, Manage Controller Bindings, choose the game, edit its binding, and on the right hand bind the Oculus Button. A game that uses OpenXR, such as Pavlov, must be running first: until it is, SteamVR cannot load its controls, and the page says "Unable to load action manifest" or stays on loading. cv1touch ships none of SteamVR's or Oculus's files: installing the SteamVR driver (`cv1touch steamvr install`, which both installers run) makes the driver's input profile from the installed SteamVR's own Oculus Touch profile. It adds the button, makes the controller type cv1touch's own with Oculus Touch as its compatibility mode, and leaves out SteamVR's Oculus Touch remapping, because SteamVR ignores a compatibility mode beside one. That remapping converts bindings made for other controllers, such as Index or Vive controllers, for a game that has none for Oculus Touch; such a game may have no bindings for these controllers until you make one. On that binding's Options, SteamVR can also, for that game, report Oculus Touch controller info, an Oculus model name or the full Touch model, and a Rift headset. Those are SteamVR's own settings for Oculus Touch; in SteamVR 2.18 they name Quest 2 controllers. The controllers are still drawn as CV1 Touch controllers unless that binding's render-model option is the full model. A live test showed the CV1 models. Games that use neither SteamVR Input nor OpenXR keep SteamVR's Oculus Touch legacy bindings. The names SteamVR shows for the controller type and the button come from a small localization file of cv1touch's own. The dashboard bindings that profile names are copied beside it when those files are there (a name with no file is left out, as SteamVR leaves it). When that profile already has `/input/home` as a right-hand button with click, that source is kept as SteamVR wrote it, including a touch that button also declares (the driver publishes only the click, as it does for the left Menu button); any other `/input/home`, or a profile that is not for Oculus Touch, stops install, check and doctor until cv1touch is updated. The button's place on the binding picture is the left Menu button's, taken from SteamVR's profile. If SteamVR was not found, `cv1touch steamvr install` (which both installers run), `cv1touch steamvr check` and doctor stop before changing anything and say to install it from Steam, or, if it is installed, to start it once so it records where it is installed, or to set `CV1TOUCH_STEAMVR` to its folder. If its Oculus Touch profile is missing, they say to have Steam verify SteamVR's files. The Linux installer then says to run `python3 scripts/install.py` again. `cv1touch steamvr check`, `cv1touch steamvr install` and doctor say to quit SteamVR and run `cv1touch steamvr install` (on Windows: choose Finish setting up cv1touch in the Start menu). The Windows installer's own note says to install SteamVR and start it once, or to have Steam verify its files, and to quit it while cv1touch is set up. `cv1touch doctor`'s `input_profile` check checks the installed profile, names and bindings. A file changed after cv1touch installed it is named as such, and the advice is to back up those changes and remove the driver package before installing again, because install will not replace it. A file that is still as installed is missing or out of date after a SteamVR update changed SteamVR's profile or its dashboard bindings for Oculus Touch, or after cv1touch changed, and then the advice is to install the driver again. `cv1touch input-test` asks for the button too, and says to bind it in SteamVR with the game running (Settings, Controllers, Manage Controller Bindings, the game, right hand, the button named Oculus Button) before checking it in that game. `cv1touch inject right system` presses it. The driver package's ownership record is now version 2: a cv1touch from before this cannot upgrade or remove a package this one installed, so run `cv1touch steamvr uninstall` with this one before going back. Bindings made for Oculus Touch (cv1touch) stay saved in SteamVR, unused by an older cv1touch, whose controllers are SteamVR's Oculus Touch.
- Sensor video diagnostics distinguish raw capture from usable JPEG decoding. `status --json` adds nullable `video_format`, `frames_decoded` and `frames_dropped` per sensor, plus `sensor_video_quality`. USB2 sensors use JPEG in normal tracking and calibration; doctor, report and board rates use accepted decoded images for them and received frames for raw sensors. Missing format or decoding metadata is not verified. Rejected-image counts are independent of queue drops; three or more between comparable one-second samples produce a warning without failing advancing video. Rejections remain visible when another camera needs more samples; the threshold applies to each interval separately. Raw delivery and camera exposure timestamps are unchanged. JPEG damage detection remains partial: some corrupt images decode without a warning.
- `cv1touch status --json` keeps each sensor's last video start attempt in `sensor_streams`, including attempts whose sensor object was freed. Serial matches ignore ASCII letter case. Each record names the error kind, raw start error, available caller error number and the USB setting that attempt used if it succeeded; `scope` marks it as a last-start result, which can remain after unplugging. `doctor`, human status and `report` use fresh USB presence and advancing counters to check current video. Caller errno `ENOSPC` after either a Linux USB alternate-setting call or transfer submission is described as "most likely not enough USB bandwidth on this controller", since libusb logging can change errno before it returns. When USB presence cannot be checked, a retained error is labelled as from the last start. This does not change USB bandwidth, retry behavior or the shared-memory layout.
- `cv1touch doctor` checks every sensor in the daemon's active calibration over up to four video samples a second apart, leaving out sensors the daemon was told to ignore. Raw video uses received frames counted before analysis: releasing old queued work cannot make a stopped camera pass. JPEG video uses accepted decoded images after exact GRAY8 layout validation. Received and decoded counts are 64-bit; a decrease or format change starts a new sample. The check names unplugged sensors and connected sensors sending no video, with cable/controller and restart advice; an unreadable USB identity is reported as unknown presence, even when the daemon retains a counter, and extra uncalibrated sensors do not fail it. `status` shows confirmed failures while pending cameras keep being sampled, and its frames/s uses received raw frames or accepted JPEG decodes. An older daemon without the required video format/counters is reported as not verified, with a restart instruction; its released-buffer counters still feed the board's labelled legacy rates. An engine that is starting or reloading stays checking during sampling; if required video still cannot be checked, doctor and report fail the check as not verified, with headset USB/power and daemon-log advice. An unavailable video counter is reported for its camera without hiding other cameras' confirmed failures. `report` includes the check. No awake controllers or pose fixes are needed, and USB settings and tracking accuracy are not changed.
- When a controller's radio goes silent while it is in use (it turned in the 3 s before), or comes back after 0.5 s or more within the 10 s it is held, the daemon saves what the radio delivered from 20 s before its last report to 10 s after, and the haptic commands sent meanwhile, as a recording in the state directory (`dropout-<unix time>-<hand>.rec`, the newest ten kept, on a thread of its own), and logs where; a gap under 0.5 s that ends is a blip and is not recorded. A dropout that begins after an earlier recording's window is recorded too, even while that one is still waiting to be saved. A still controller that goes to sleep is not recorded: the daemon waits up to 1.25 s after its last report for the sleep beacon a sleeping controller sends before it logs `radio silent (still)`, logs `asleep` instead when one comes, and `cv1touch status` shows it as asleep (SteamVR's log still says `radio silent: held as it was`); it is held the same 10 s. A still controller that comes back after 10 s or more was in standby and is not recorded either. When the daemon passes a controller between its reading threads during a gap, or reopens the tracking engine, it cannot always prove a nap, so it records such a gap to be safe: some of those recordings are ordinary naps. A still controller that stays away 35.5 s or more is not recorded: by then the radio's traffic from before it went silent may no longer be in memory. A nap confirmed before an engine reopen stays unrecorded, and an engine reopen or a stalled tracking thread never saves a recording itself. It keeps the radio's last minute in memory for this, in a fixed ring the radio thread copies each report into without ever waiting: a report that arrives while a recording is being copied out is left out of the ring. The save log and `cv1touch rec-summary` say how many reports and haptic commands were left out of a recording that way, normally none, or that some may be missing when the daemon could not count them; older tools still read these recordings. A dropout none of whose radio traffic is still in memory is not saved, and the log says it was too old to record. `cv1touch report` sends the newest three; they hold no camera images. Recordings (`cv1touch record`) now also hold the haptic commands the daemon got (record type 8).
- The headset alignment measures where the base station SteamVR tracked the headset from is in the cv1touch world. Captures record, from SteamVR's log, the station each Lighthouse device was tracked from throughout (`tracking_bases` in the truth file), and the registration keeps that station's world pose along with those earlier alignments against the same calibration measured; one SteamVR moved during the capture is not measured, an alignment that measures no station keeps none, `register --stations` and `calibrate rig` clear them, and the levelling of `calibrate gravity` turns them with the world. The daemon follows a measured station as closely as the alignment measured it. A station no alignment measured is placed by the mean over SteamVR's settled layouts of where each puts it relative to the measured stations: on one setup a single layout puts a station 2 to 17 cm off over the play area, and the mean of seven about 1 cm. While the history holds fewer than eight layouts, an alignment adds those its earlier captures saw. `cv1touch register --follow` takes `--tracking-base LHB-SERIAL` for a capture made before captures recorded the station.
- `cv1touch setup --redo STAGE` offers a finished stage again, with redo and keep (`sensors`, `floor`, `model`, `buttons` or `headset`), for redoing one step with the guide after something changed that the guide cannot see, such as a new SteamVR room setup; its saved result stays until the step is redone, and quitting at the prompt changes nothing.
- A sensor that is moved, bumped or re-mounted is recalibrated by the daemon itself while the controllers are tracked, with nothing to do, as long as two or more sensors stayed put. Each sensor's matched LEDs are checked against the pose the others set (a controller nearer than 0.6 m is no check); missing sightings only ask the engine to identify the controllers in that sensor's view while it is still tracked with, and observed disagreement over two windows of 5 s, or across an inspection, stops it being tracked with. Its frames are then gathered as probes (the controller as the others track it, with the LEDs the engine labels), and a pose placed from them and confirmed by a second batch within 10 mm and 0.5 degrees is tracked with at once, given to the engine, and written into the calibration (the old file kept as a backup; the sensor's landmarks are dropped). `cv1touch status --json` shows each sensor's `pose` state and `sensors_unsure`; `cv1touch doctor` gets a `sensor_poses` check. A pose placed within 3 mm and 0.2 degrees of the calibrated one is a false alarm: nothing is written and the sensor is tracked with again; so is a sensor that sees no labelled controller for 30 s or gets no pose in 3 minutes, and a sensor placed three times in half an hour is given up on. The calibration file is written only while `cv1touch setup` is not running and only when it is still the file the daemon loaded; the stages `setup` had completed stay completed, and of the backups the daemon's own writes make only the newest ten are kept (other tools' backups are never touched). With no pose that holds up after six batches, the daemon says to run `cv1touch setup`; with fewer than two agreeing sensors, it and `cv1touch doctor` say that cv1touch is still checking whether a sensor moved, and to run `cv1touch setup` if that lasts several minutes.
- `cv1touchd --supervise` runs the daemon as a child process with each line of its output stamped with the time in `logs/cv1touchd.log` under the state directory, keeping four earlier logs. After a failure it starts the daemon again 2 s later, as the systemd unit does, unless the daemon refused its arguments or failed five times in a row within 30 s of starting. It is meant for Windows, where no service manager does this.
- A Windows installer, `cv1touch-setup-<version>.exe` (Inno Setup; built by CI from the Windows bundle `windows\bundle.ps1` collects). It installs for the person running it, with no administrator rights, gives the sensors their driver (`cv1touch sensors install`, one permission prompt), registers the SteamVR driver and starts the daemon, which from then on starts at logon without a window through the new `cv1touchd-quiet`. A step that does not finish (no sensor plugged in, SteamVR running, not found so it must be installed and started once, or its files need verifying) is said at the end, and the Start menu's Finish setting up runs both again; the Start menu also gets Set up, Check, Send a report, Start and Stop. The uninstaller stops the daemon, unregisters the driver and takes the sensors' driver off; settings and calibration stay. The bundle carries the terms of every library the Windows build links in (`third_party\licenses`, see `THIRD_PARTY_NOTICES.md`). `docs/windows.md` tells a tester what to do.
- `cv1touch sensors` says whether each Rift sensor plugged in can be used: on Linux, that the udev rules let it be opened. On Windows, where the engine reads the sensors through WinUSB and Windows gives them no driver of its own, `cv1touch sensors install` gives each sensor's two interfaces Windows' own WinUSB driver (the Microsoft-signed "WinUsb Device", as choosing it in Device Manager does; no other driver or certificate is installed), asking Windows for permission once, and `cv1touch sensors remove` takes off what it gave, leaving a WinUSB someone else set up alone. Both say so, and exit with code 3, when a program was using a sensor and Windows must be restarted to finish. `cv1touch doctor` checks it on Windows.
- `cv1touch report` saves one zip file with what someone helping you needs to see what went wrong: a summary (version, system, the `doctor` checks, the Oculus USB devices and the drivers they run with, the daemon's status and setup's state), the ends of the daemon's and SteamVR's logs, and cv1touch's settings and calibration. On Windows it goes on the desktop and Explorer shows it; elsewhere it goes in the current directory, or wherever `--out` says. It says what it holds: SteamVR's log also names your other VR devices, your user folder and your network addresses.
- `cv1touch stop` stops the daemon cleanly, as SIGTERM or Ctrl+C does, and with it a `cv1touchd --supervise` running it, and waits until both have ended (10 s at most; exit code 2 when one still runs), so that what comes next finds their files free. The supervisor itself stops the same way: Ctrl+C or SIGTERM asks the daemon to stop, and ends it if it has not stopped 10 s later. Closing the supervisor's console window leaves the daemon 5 s, as Windows then ends the supervisor, and logging off ends both at once; `cv1touch stop` is the clean way.
- `cv1touch tilt DEGREES` shows the controllers pitched from their tracked pose, positive with the forward end up, within +-45 degrees, for applications that hold a tool in the hand at a fixed angle and offer no way to change it (a gun pointing too low or too high for your grip). The pose SteamVR hands applications and the render model pitch together, applied at once, kept across daemon restarts in `settings.json` as `tilt_deg` and shown by `cv1touch status --json`; `cv1touch tilt 0` shows them as tracked again. Nothing about tracking changes: the render offsets `cv1touch fit-render` fitted are turned by that pitch when published.
- `cv1touch prediction [PERCENT]` sets how much of the tracked motion SteamVR extrapolates poses with: 100 (the default) as before, 0 none, so each pose is shown where it was measured. `cv1touch prediction position PERCENT` and `cv1touch prediction rotation PERCENT` set positions and orientations separately: positions as tracked keep the controllers with the body on a sidestep, while orientations shown where they were measured were the way around a tilt during fast turns (fixed below). Settings apply at once and are kept for later runs in `settings.json` in the configuration directory (`rotation_prediction_percent` for orientations; a file without it means the same for both). The driver applies them, whichever poses are published (also OpenHMD's): daemon and driver must be updated together (shared-memory ABI 4).

### Changed

- Clock fitting no longer copies its retained samples into a temporary allocation on each mature refit; the fit and timestamp mapping are unchanged. See [verification](docs/clock-refit-performance.md).

- Shifted optical association scans for a unique nearby blob instead of allocating and sorting a temporary distance list for every LED and candidate shift. Matching behavior is unchanged. A local synthetic recovery benchmark took about 26% less time per association; this is not an end-to-end latency measurement. See [verification](docs/shift-association-performance.md).

- Optical tracking skips intermediate covariance inversions within each iterative update, keeping the same final state and covariance. A release benchmark of three- and four-iteration optical fits took about 28% less time, and one 30-second offline replay about 9% less; single-iteration updates do the same matrix work. This does not measure display latency.
- The driver computes the exact pose-age percentiles without sorting every sample. Synthetic 1,000- and 10,000-sample reports with random ages and handoffs ran about 2.9 and 4.2 times faster in a local optimized benchmark. Diagnostic text and the ten-second reporting interval stay the same; this does not establish an end-to-end tracking latency improvement.

- The daemon avoids temporary heap allocations when a controller's factory-calibration identity is unchanged. Identity queries keep their order and frequency, and input resets on replacement and calibration fallback keep their behavior. An offline adapter benchmark removes two allocation and two reallocation calls per unchanged query; no display-latency improvement has been measured.
- The latency adjustment, `cv1touch latency MS` (how much earlier than their measured time published poses are stamped, on top of the 4 ms the pipeline measured for the radio link; a negative value stamps them later), is kept across daemon restarts in `settings.json` as `latency_adjustment_ms`, shown by `cv1touch status --json` and logged when the daemon starts with one; before, it lasted until the daemon was next started. The reply says which way the stamps move. `cv1touch eval` says, under the lag it measures between the published stamps and the Lighthouse-tracked reference on the jig (negative: the Touch runs ahead of the reference), the `cv1touch latency` value that puts the Touch on the reference's timeline (captures record the adjustment they were made with, so the value is absolute; for older captures it says how much to add), and leaves a lag within 0.5 ms alone. Which timeline is the true one it cannot tell. The driver submits a pose stamped after the submission itself as current, so an adjustment that stamps poses later than their samples arrived (below about -4 ms) has no further effect.
- The SteamVR driver's log line on the age of the poses it submits (every 10 s in SteamVR's `vrserver.txt`) now also says how much of that age passed after the daemon published the pose, which separates the driver's own wake-up from everything before it (the radio link and the daemon).
- IMU stillness checks no longer allocate a temporary window. In repeated local synthetic 500 Hz benchmarks, detector CPU time fell by about 30% and the complete IMU call by about 17–18% with empty camera bookkeeping; populated camera cases are also measured in `docs/stillness-performance.md`. Window boundaries, tracking decisions and sampling cadence stay unchanged; these are offline CPU measurements.
- Controllers are tracked again sooner after waking up or losing their position. The tracker also starts from OpenHMD poses rated good, not only strong, and after a loss it searches for the controller's position itself with the orientation the gyro kept. A track started either way is shown only once a second sensor, or a strong OpenHMD pose that agrees with it, confirms it. Replaying recordings from 2026-10-08, wake-ups that had taken 6.6 s and 2.9 s took 0.24 s and 1.5 s and the other three 43-63% less time, with no new wrong locks. `cv1touch status --json` counts these acquisitions (`good`, `searched`, `unconfirmed`).
- `cv1touchd` no longer runs OpenHMD's brute-force pose search for a controller its own tracker fitted within the last 100 ms, or one asleep, except on a sensor that has no pose yet. That search took most of the daemon's CPU time during play. The per-sensor OpenHMD fix counts in `cv1touch status` are lower for tracked controllers as a result.
- Reading controller battery reports avoids one temporary allocation when a report contains battery updates. Battery values, message order and change logs stay the same; this removes a small amount of CPU work, with no measured end-to-end latency change. See the [offline measurement](docs/battery-radio.md).

### Fixed

- Saving a re-placed sensor's pose, or asking the engine to look for a controller on that sensor, could stall controller tracking. The radio thread queues that work, and the engine held the queue lock through the save and the inspection. The engine now takes the queued work out of the lock first. The bias-file hand-off releases its lock the same way, so the radio thread can wait on it only when one save blocks for about 30 seconds. Installing a controller's LED model, which the engine hands over on the same kind of lock, happens after that lock is released too. A status reply now copies the radio thread's queue, landmark, pose and input state before the reply is built and formatted, so that work does not hold those locks. An inputs reply copies the latest samples the same way. What is saved, and when, is unchanged.
- Starting a sensor no longer logs that it received about 145 to 157 damaged packets in 10 seconds while waiting for an image boundary, and no longer throws away the first image. The first packet after a sensor's stream opens is left over from an earlier stream: its timestamp is from before this stream's clock started. The first image arrives about a second later with frame ID 0 and a new timestamp. When the leftover packet also had frame ID 0, that whole image was rejected as out of sequence. On three five-sensor starts that happened on four, four and two sensors, one image of 145 to 157 packets each (a complete image plus its 12-byte end header). That image is now kept when both the leftover and the image carry a timestamp. A frame-ID change that does not also carry a new timestamp is still reported, and an incomplete or otherwise damaged image is still discarded. An opening packet with no timestamp still does not keep that image.
- A lock released by cv1touch could stay held for a moment while another part of the same program was starting a process, so tests found it busy, and in rare timing `cv1touch setup` started just as the daemon finished saving a re-placed sensor could have said another setup guide was running. Locks are now released as soon as their owner lets go of them.
- Reopening the engine now holds a controller that was live, with its pose frozen and all inputs as they were, for the same 10 s from its last sample as a radio gap. The hold starts before waiting for the radio thread, continues through initialization and a blocked first update, and expires even while opening or closing the engine blocks; retries do not start another 10 s. A hand passed to the radio thread stays refreshed through silence even before that thread has a sample of its own. Hand state and expired inputs are published before logging, with no hand lock held while a log line waits. The native engine reopen took 6.6–6.9 s on one five-sensor setup. Fresh samples resume normally, and stopping the daemon disconnects both hands immediately. The log says the tracking engine is reopening, or that a tracking thread stalled, rather than that the radio went silent, and such holds save no dropout recording; a radio timeout already reached before teardown stays a radio gap, even between refreshes. The heartbeat never waits for a busy hand or input lock, and tracker work leaves the publication lock free. Passing a hand between the engine and the radio thread starts no gap while the controller still reports. Only the daemon's own notices distinguish these causes: during an engine reopen, `cv1touch status` and SteamVR's log still say `radio silent: held as it was`. Cause-specific status and driver wording need the shared-memory flag follow-up.
- Sensor status stays empty after shutdown, even if an engine update finishes late. The in-memory list and shared-memory sensor block are written under the same lock, so concurrent publications cannot leave readers with a torn snapshot.
- `cv1touch` and its status board explain control connection failures in plain words: how to start a missing daemon, which socket belongs to another user or has the wrong permissions, or how long a request waited and where to find the daemon's log. The board keeps the reason alongside its shared-memory fallback. Stop distinguishes an absent daemon from one running without a reachable control socket, and availability checks omit start advice. Exit codes, request deadlines and refresh timing are unchanged.
- Reading a huge or fast-growing SteamVR log no longer grows the daemon's memory without limit, and a blocked supervisor log or terminal cannot hold up tracking, child restarts or shutdown. The daemon reads SteamVR's log in 64 KiB pieces and skips lines longer than 8 KiB. If lines or events are skipped, it stops trusting the last named headset base station and follows the stations together until SteamVR names it again; `cv1touch universe` explains why, and the daemon mentions it at most once a minute. Ordinary tracking loss keeps the last named station. The supervisor shortens lines to 8 KiB, holds at most 1024 waiting lines and drops and counts excess output. Its current log stops growing at 16 MiB even if it cannot start a new one. It recovers interrupted log moves without overwriting files and retires the oldest saved log only after the others are in place. A blocked log produces a plain notice naming the path and remedy; an unavailable logs folder or current log still lets tracking start, with a notice on the supervisor's own standard error, counted output loss and opening retried once a second. Once fixed, logging resumes on its own and reports lost daemon lines. One writer handles files and notices through the bounded queue and is never waited for past the one-second exit drain. If that writer cannot start or stops unexpectedly, it is retried once a second and reports the problem when it can write again. Failed terminal writes also back off; recovering a writable current log does not have to wait for a blocked archive. One supervisor owns a logs folder across runtime directories; another still runs its daemon while dropping and counting output until ownership is available. `cv1touch report` lists log and staging names and sizes. Existing oversized logs are left intact. A staged current log can still need manual action if recovery was refused and a new current log occupies its old path; both logs are preserved and tracking continues. Recovery does not cover power loss.
- Starting the daemon with `--record PATH` makes its control socket available while the recording opens, and reserves that session before serving another recording start. Opening and the header run on the recorder writer; a failure still stops the daemon with a non-zero exit, cleaning up its control sockets and retiring shared memory. Errors during the final storage wait still exit non-zero; a timeout says the file may be incomplete. If the daemon is asked to stop before it has started tracking, the original session's final result remains fatal after a sync failure even if a client has acknowledged it and started another recording. A startup failure is logged once by its writer, even if closing the file stalls. Hardware is opened only after the header succeeds; the recording size and disk-space limits still apply. A status request while it logs that it is running no longer risks hanging the daemon.
- A recording on slow or stalled storage no longer holds up haptics, status or daemon stop. A recording start reserves its session before opening storage, so shutdown can cancel a pending start. Recording stop waits up to 30 seconds outside the control lock (daemon shutdown waits at most half a second), reports when the file is still finishing or writing/syncing failed, and refuses a replacement until the old session's outcome is acknowledged. Recordings stop at 8 GiB (16 GiB with camera pixels) or before using the disk space kept free: 5% of its capacity, at least 2 GiB and at most 20 GiB. A size or space stop saves a complete, synced prefix and says it ended early; setup and calibration do not fit that shortened capture. Guided setup waits for a pending recording to be stopped and its result acknowledged before changing stage progress or preparing a capture. The limits apply per session and do not remove older recordings. The writer logs write or sync errors and size or space stops once; shutdown adds a separate warning if the file may still be incomplete. Update the CLI and the daemon together (the installer does); an older `cv1touch` can use an unfinished recording if storage stalls for over 5 seconds. After a Linux upgrade, restart the running daemon with `systemctl --user restart cv1touchd`; automatic captures refuse an older daemon that cannot confirm completion.
- `cv1touch register --holds/--follow --reference SERIAL` and `register --follow --tracking-base SERIAL` prefer an exact recorded Lighthouse serial. A different letter case is accepted only when it names one recorded device; an ambiguous name lists the candidates and asks for an exact spelling. Saved names keep SteamVR's spelling.
- Sensor serials match regardless of ASCII letter case, in the engine and in the daemon's own tracker. `--ignore-sensor camera1` now leaves CAMERA1 closed (it used to stay open), and a calibration entry written `camera1` places the camera the device reports as `CAMERA1`, also when the daemon saves a pose it placed again; discovery treats differently cased names as one sensor, and published serials keep the spelling the device reported. Calibration commands, recordings and landmark monitoring use the same identity; re-placing a sensor keeps its saved serial and its role as the reference sensor. Two entries that differ only in letter case are one sensor, so a calibration that lists both, or a camera named twice with `--ignore-sensor`, is refused with a message naming them.
- Incomplete sensor images and damaged video packet sequences are discarded before tracking can mistake old pixels left in a reused buffer for controller lights. Even a raw image missing one byte is rejected; complete raw images still reach analysis as soon as their final byte arrives. A USB 2 JPEG image is discarded when the decoder reports that its data ended early or was corrupt, which it would otherwise fill in with invented pixels; an image with a harmless decoder warning, such as padding before its end marker, is kept. An error flag on an image’s opening packet discards that image, and a JPEG thumbnail cannot end the main image early. Instead of a line per damaged packet, the daemon log reports discarded images per sensor and reason at most once every 10 seconds; malformed packets and extra raw image data are also reported when no new image starts. This does not recover missing camera data or increase USB bandwidth, and the decoder does not notice every kind of JPEG damage.
- The daemon no longer treats an unseen controller as a moved sensor: it keeps tracking with that sensor while the engine works out which controller the sensor sees, which needs each controller to turn on its own. Only LEDs a sensor matched, or labels confirmed that way, can show it disagrees with two other sensors; a check finds it moved when 60% or more of at least 80 such sightings over two or more five-second windows disagree. A sensor found moved during another's check is handled first, unless some controller sightings are taken back before then, which the log says. Sightings credited to the wrong controller are taken back once the two turn differently; before that, they can get a sensor judged moved and then found where it was, or enter a placement under way, whose second batch rejected four seconds of them in testing. The movement log line gives the sightings that decided it; `cv1touch status --json` adds `observed_checks` and `observed_misses` to each sensor's `agreement`: how many checks used LEDs that sensor itself matched, and how many of those disagreed. Recordings (`cv1touch record`) also hold the engine's controller identification notices, each engine open and each retirement of identifications (record types 9 to 11), which older readers skip. In development replays of nine recordings (not in this repository), unmoved sensors gave no still-checking windows or wrong moves, versus 28 still-checking windows and one wrongly moved sensor before; with both controllers held rigidly together, an unmoved sensor keeps its calibrated pose, where before it was wrongly taken out of tracking; a sensor 0.4 m off was found at 25 s and placed at 48 s, versus 15 s and 25 s before, the cost of telling the controllers apart. A replay (`cv1touch track`) does not check sensors for movement and counts a search result more than 0.4 s after its frame as too old, so its counts can be lower than the daemon's. See [how the check works and its limits](docs/self-recalibration.md).
- The SteamVR driver logs the first failed haptic delivery even during the first minute after boot. Later delivery warnings keep their one-minute limit.
- On Linux, a runtime directory so long that the control socket's path passes the 107 bytes Linux allows is now explained, where before `cv1touchd` printed a `SUN_LEN` error, SteamVR's log only suggested that the daemon was not running and `cv1touch` printed `invalid control socket path`. `cv1touchd`, and `cv1touchd --supervise` before it creates anything, say they cannot start, whether `--runtime-dir` or `XDG_RUNTIME_DIR` built the path, and give its length and full path. The SteamVR driver says it cannot reach `cv1touchd`, so haptics and base station updates do not arrive, and to start SteamVR with a shorter `XDG_RUNTIME_DIR`. `cv1touch` commands that contact the daemon, including input calibration, registration, captures and setup checks, give the full path, its byte count, the limit and advice to use a shorter `XDG_RUNTIME_DIR`; reports keep that diagnosis too. Which socket is used is unchanged: a path that is too long still does not fall back to the shared socket in `/dev/shm`.
- A stalled system log no longer freezes the controllers or prevents the daemon from stopping. Logging uses bounded memory and discards excess lines with a count when output resumes. A failed native assertion or a panic in a native callback still ends the daemon for its supervisor to restart, even when the log is stalled. Native engine messages now share standard error with the daemon's Rust messages (previously they went to standard output); their prefixes stay as before.
- Control requests give up within the caller's timeout even when the daemon stops accepting connections. Connecting, sending the command and reading its reply share one deadline on Linux and Windows; a reply arriving in pieces does not restart the timeout.
- The supervisor keeps output it already received ahead of later messages when a loaded machine schedules it after the one-second pipe-reader cutoff, even if something the daemon started keeps its pipes open and continues writing. The bounded writer drain at supervisor exit can still leave queued lines unwritten.
- The supervisor gives the daemon ten seconds to accept a stop request and, if it accepts in time, ten seconds to stop. Failed attempts share the original deadline, and a late reply cannot postpone ending the daemon. Closing the console still leaves only the time Windows allows.
- Controller factory-calibration caches are saved through a sibling temporary file on Linux and Windows, then moved into place, so a reader sees the old cache or the complete new one, and a failed save keeps the previous cache or leaves none. Nothing is synced to disk: a save runs on the tracking thread, which must not wait for the disk, and a cache torn by a power cut fails to parse and is read from the controller again. The saved file has the permissions an ordinary write gave it (the umask applies). A save that fails, for example in a read-only or full folder, logs one warning that names the file and the reason and says the calibration is still in use and will be read from the controller again next time; it does not restart calibration reads. Two processes creating the cache folder at the same moment no longer fail the save on Linux. Windows cache paths skip UNC and extended roots during directory creation and use backslash separators, with distinct permission, missing-path, out-of-memory and full-disk errors. Cache names and when caches are loaded and saved are unchanged.
- Haptics and base-station reports reach the daemon when Linux SteamVR runs inside Steam's pressure-vessel container, which hides the usual control socket. The driver can also use a private socket beside the shared-memory poses and remembers which socket it reached, without retrying a command that may already have arrived. Both the daemon and driver need this update for container support; either still works with an older counterpart outside the container. Instances started with an explicit runtime directory or shared-memory name keep their own control endpoint. Pose transport and Windows are unchanged.
- Paced accuracy captures (`cv1touch eval-capture`) keep the base stations' poses alongside the selected Index controller, as free captures do, so a registration fitted with `register --follow` has stations for the daemon to follow when SteamVR changes its layout. Both capture modes timestamp each pose when it is read and check devices one index at a time, instead of pausing the pose stream for a full inventory scan. Poses are kept only after the next identity check confirms the device number still belongs to the same device; an interval whose reported identity or tracking validity changed is discarded. The timestamp and device-number fixes also repair free captures. The selected reference and truth-file format stay the same; older captures are unchanged.
- The daemon no longer runs out of file descriptors after many hours with SteamVR closed, leaving it unreachable and making `cv1touch doctor` fail its daemon check. The universe watch checks for SteamVR's server before connecting: failed OpenVR starts can leak descriptors inside SteamVR's library. Failed connections are retried after 60 s, then with the wait doubling to at most 15 minutes, even if driver reports arrive and go stale meanwhile. Process checks run only when a connection attempt is due; once the server is found stopped, they run at most every 10 s. A successful connection or a stop detected at the next check resets the backoff. `cv1touch universe-watch` shows whether it is waiting for SteamVR or retrying, and how long until the next check. The setup guide also checks that the server is running before each retry. A daemon that has already exhausted its descriptors still needs to be restarted.
- The daemon's landmark check measures one coherent sensor displacement over a 2 px range, rather than clipping each spot to within 0.8 px of its old reference. Isolated 1.1 and 1.5 px moves can now reach the single-landmark warning. Two or more uniquely matched spots can measure a shift when another station is hidden. Supporting patterns with a competing correspondence at any translation remain unknown, including partial repeated patterns that only an absent emitter would disambiguate. The uniqueness check also considers multiple modes coming from one emitter, so a split mode cannot masquerade as independent landmarks. Rounding at the numerical limit cannot discard a competing correspondence. Unknown windows clear old status without announcing recovery. The [measurement guarantee](docs/landmark-watch.md) assumes observations of genuine learned emitters with mode centroid errors bounded by 0.4 px; pixels alone cannot detect spurious sources that counterfeit a learned pattern. Window analysis runs on a bounded background worker, keeping it off the radio thread; an internal error in one analysis leaves that window unknown and is logged once, without stopping the check. This check only reports movement: tracking, automatic re-placement and the warning thresholds are unchanged.
- The daemon reports a sensor's landmarks moving once per alert, after two consecutive one-minute windows over their threshold, and recovery once the shift falls below that alert's threshold with at least as many landmarks as when it was raised. A persistent shift between 0.4 and 1 px repeated the recovery notice every minute, and losing landmarks could falsely announce recovery by switching to the higher single-landmark threshold. More landmarks may tighten an active alert's threshold; fewer cannot clear it. A window without landmarks breaks a pending movement streak and leaves an active alert alone. The threshold values and tracking are unchanged.
- If the tracking engine thread stops unexpectedly or the radio thread panics, the daemon says which thread stopped and exits with a failure so its supervisor can restart it with fresh state, even if startup fails or closing the engine or radio stalls. Missing devices, late device permissions and ordinary USB disconnections still wait or reopen the engine as before. If a radio decoder cannot be created, it publishes the engine's poses without opening the radio. The checked-in systemd unit now uses the same 2 s restart delay as the installer; no new start-attempt limit is imposed.
- Dropout recordings use one writer with at most two pending recordings. Stalled storage keeps gaps that began in use ahead of still gaps, keeps the newer ones at the same priority and logs any loss instead of starting more threads; the recording already being written is kept. The history of sensor re-placements keeps only the half hour the daemon uses to decide whether to try again.
- Idle control clients release their slots after 2 s; sending a partial request does not extend that deadline. Complete requests can keep a connection open, and driver haptics and station reports keep using a fresh connection per request. Requests longer than 4 KiB are closed before they are handled.
- Malformed or truncated Touch factory calibration, and failed calibration-file reads on Linux, no longer leak memory. Invalid cached data falls back to the controller; temporary allocation failures retry the same cache. Terminal failures wait 1 s after completion, doubling to at most 60 s, and warn from the second consecutive failure, then only when the hand, source, field or reason changes, with the retry delay and next step. One missed answer on wake-up is retried quietly. Sleep and queued reports keep that history; success or an observed new calibration hash resets it. A replacement controller is checked at the next scheduled retry, up to 60 s later. Pending reads continue without controller reports: each radio request gets 5 s to be answered, and every block that arrives restarts that wait, so a full download can take longer. A request that finished while the engine thread was stalled is read, not given up. After a timeout, or after a vibration request whose status could not be read, the radio's old reply is read and thrown away before another request is sent, so it is never taken as the answer to the next one; the radio cannot cancel a request, so one that never finishes keeps calibration and vibration waiting. While an old reply is pending, both controllers and vibration share checks spaced at least 100 ms apart; a drain still waiting after 10 s warns once. Short status replies cannot confirm reads or vibration. USB failures report input/output errors, and stale numeric errors cannot poison later parses. Calibration is rejected before it is used when its root is missing; a stick, trigger or grip range endpoint is missing, not a whole number or out of range, or the endpoints are reversed or not strictly increasing; a touch-sensing list has fewer than 8 entries, an unusable value in a used slot, or a touch value equal to its resting value; or its IMU or LED data is unusable. Missing dead zones disable the clamp, missing IMU offsets default to zero with one warning, and unused touch-sensing slots are ignored.
- A controller whose radio goes silent for a moment no longer drops out of the game. After 100 ms without a report the daemon told SteamVR that the controller had disconnected and released its inputs, so a game let go of whatever the hand held; on one setup the right Touch went silent three times within 11 s during a match, for 0.5 s, then 7 s, then for good. A controller whose motion samples stop now stays connected for up to 10 s, out of range, where it was, with every button, the trigger and grip held as they were when its reports stopped; when they resume it carries on, and after 10 s it is in standby and its inputs are released as before. The daemon logs when a controller's motion samples stop, whether it was in use then, and when it is back, and `cv1touch status` shows such a controller as held. A still controller is logged as `radio silent (still)` only after 1.25 s without a sleep beacon; one that sends sleep beacons is logged as `asleep` and later `awake again`, and shown as asleep, with the same 10 s hold. If the daemon passes it between its reading threads or reopens the tracking engine meanwhile, it cannot always prove the nap and may record it. Drivers that do not know about sleep keep working. The daemon and the driver must both be updated for the whole of it: an older driver lets go of the controller after 1 s.
- The controllers no longer sit centimetres off the headset after SteamVR re-solves its base-station layout, which it does at nearly every start. SteamVR tracks the headset in the frame of the base station it bootstrapped from and re-solves the stations' poses relative to each other, by different amounts each time (one station by 110 and then 120 mm within a minute on one setup), while the stations stay where they are mounted. The universe watch followed the stations' moves together, so after a re-solve the controllers sat where no single station put them: on one setup's headset-alignment captures under four layouts it predicted each capture's registration from another's to 5 to 82 mm, against 13 to 134 mm without following. It now follows only the station SteamVR tracks the headset from, which SteamVR's log names (`vrserver.txt`, found through OpenVR's path registry), from where that station is in the cv1touch world; on the same captures, with each station placed by other captures, that predicts each to 2 to 7.5 mm. Through a moment without tracking it keeps to the last station named, and without the log it follows the stations' moves together as before. A registration made before this places each station where the layout it was fitted in puts it, which is right for the station SteamVR tracked the headset from at the time. The daemon also keeps each layout SteamVR settles on (one it keeps for two minutes) in `station-layouts.json` in the state directory. `cv1touch universe` says which station SteamVR tracks the headset from, how each station's place is known and how far SteamVR's layout now puts what each station tracks from where the headset's frame has it; `cv1touch universe-watch` says what the registration follows.
- `cv1touch register --follow` fits a capture made before the calibration was last written, which the daemon's own re-placing of a bumped sensor makes of every earlier capture. The fit replayed such a capture under the installed calibration, and the replay has nothing to start from when the daemon tracked throughout, so it failed with "never moved with the reference". When the replay tracks less than half of what the daemon published, the published poses are now carried into the installed calibration's world through the change of frame the sensors show; a sensor the newer calibration moved by more than 10 mm or 1 degree against the others is left out when three or more remain, and otherwise the capture is refused.
- The headset alignment's nod-and-tilt step no longer ends after the first tilt. It ended once the head's pitch and roll had each covered 30 degrees of range, which the circles' wobble plus one tilt toward one shoulder could satisfy; it now needs a nod up and a nod down and a tilt toward each shoulder, each at least 15 degrees from level, as the instructions say.
- Headset alignment (`cv1touch setup`, `cv1touch register --headset`, `register --follow`) no longer fails with "never moved with the reference" on a good capture. The fit replayed the capture through a fresh tracker, which has had no engine poses to start from since the daemon stopped running the engine's search for a controller it tracks, so it never acquired either Touch. The fit now uses the poses the daemon published during the capture, unless the calibration was written after the capture (then it is replayed as before, and the fit says so). `register --headset` also says that the recording runs from the start and keeps only the rigid stretch, so there is no need to be holding the controllers to the headset when the command starts.
- The controller models sit on the real controllers without a constant tilt. `cv1touch fit-render` (the controller-model stage of `cv1touch setup`) fitted the factory LED positions onto the SteamVR body mesh's surface by nearest point; the LEDs sit under a cover, and near the ring's edges the nearest surface is the ring's side wall rather than the LED's window, so the fit pulled one side of the ring in and the other out (under the previous offsets the LEDs lay from 2 mm inside to 1.3 mm outside the surface around the ring, and five per hand faced 60 to 140 degrees away from the surface they were matched to), a few degrees of pitch and a mirrored roll between the hands. Each LED is now matched to the window its emission ray leaves the mesh through, and all LEDs sit a common depth under their windows, fitted along with the pose. An LED whose ray leaves the mesh through a face that does not face it (more than 30 degrees off) is under no window the mesh models and is left out: the two LEDs on the handle leave the body mesh through faces 34 to 50 degrees off, 3 to 5 mm in front of them, and matched to those faces they pulled the fit 4.5 degrees off the ring (3 degrees of pitch and a 2-degree roll mirrored between the hands); an LED whose ray leaves through no face is held under the nearest surface until the pose brings it back under its window, and one still without a window once the others sit under theirs points out of a gap in the mesh and is left out too. With fewer than six LEDs under windows nothing is installed. The ring's 22 LEDs then sit a common depth under their windows to 0.04 mm, and the two hands' fits agree to 0.2 degrees. The report says how many LEDs sit under windows the mesh models, that depth and how far the LEDs depart from it. Rerun `cv1touch fit-render` (or the setup stage) to take it.
- Rotation prediction no longer tilts a controller during fast turns. SteamVR integrates a driver's angular velocity in the device's own frame, not in the world's as its documentation says (measured with a synthetic pose: a rate about the world's up axis was applied about the pitched controller's own axis, whatever the alignment or render offset), and the driver gave it the world rate, so every predicted turn went about an axis off by the controller's orientation, more the faster the turn. The driver now gives SteamVR the body rate. `cv1touch prediction rotation 100` is worth trying again where it was turned down for the tilt.
- A controller that has just woken up, or whose wrong lock was just dropped, no longer appears at OpenHMD's own position estimate (which could be metres off) until it is tracked again: SteamVR shows it where it was last tracked, turning but not moving. The daemon log now says how long each controller went without a position when it gets one back, and logs that after a wake too.

## [0.2.0](https://github.com/michaelkrauty/steamvr-oculus-touch/releases/tag/v0.2.0) - 2026-10-11

### Added

- `cv1touch setup` guide for camera, gravity, render, input, and headset-registration stages, with a private resumable journal and dependency-aware reuse.
- Read-only `setup --check` and `setup --check --json` reports; explicit visual-verification/adoption of legacy calibration without discarding its files.
- Controller-button and haptic checks before headset registration, with a button-started haptic countdown and B on the right controller to cancel the capture.
- Headset registration ends its recording by itself once the person has turned, nodded and tilted enough, and stops it with three quick haptic pulses when a controller turns on the headset by more than about 3 degrees within a second (or on any other problem); the retry prompt, or `setup --no-slip-check`, turns the slip check off.
- `cv1touchd` status names its shared-memory segment (`shm`).

### Changed

- Guided input calibration captures both hands in four shared phases, reducing timed capture to 16 seconds while retaining freshness, identity, travel, and save/reload checks.
- An accepted fresh guided camera solve completes gravity alignment from the same motion capture; separate still-hold gravity refinement remains available.
- Guided input calibration precedes headset registration, leaving headset movement as the final physical setup step.
- The setup guide reads like a checklist: plain stage names (sensor positions, floor level, controller model, buttons and sticks, headset alignment), checks explained only when they fail, Enter/`q` (and `k` to keep unverified saved settings) instead of typed words, one result line per stage with solver output in a log, and an immediate retry after a failure. Captures start with A on the right controller as well as Enter, timed steps are marked by a controller haptic pulse and a speaker beep, and input calibration records each step as soon as both hands are in position. Instructions say what each step is for and exactly how to do it, and failures say in plain words what happened and that the previous calibration is unchanged.

### Fixed

- Failed camera captures recover provisional tracking when the previous calibration is malformed; rejected reloads attempt recovery and report failure.
- Cancelled render, registration, gravity, placement, and refinement fits do not install their computed settings.
- Guided registration bootstraps a fresh fit after camera-world changes instead of depending on an obsolete saved transform.
- Guided camera/gravity handoffs wait for the requested engine configuration, advancing sensor streams, and fresh data from the same controllers before continuing.
- Pending setup stages retain missing or invalid artifact diagnostics instead of offering adoption of unavailable settings.
- Guided headset registration explains preparation before recording and waits for a deliberate button press and haptic countdown, so users can get into position without watching the terminal.
- Guided capture validates recording acknowledgements and scopes cleanup to its own recording when a start reply is lost.
- Guided calibration prompts identify buttons by controller, state when input sampling begins, and separate the control checks from headset instructions.
- A controller falling asleep before the registration countdown (during the button checks or while reading the headset instructions) no longer aborts setup: the guide names the controller to wake, waits up to five minutes, and then needs a fresh release and press. A dropout during the countdown or recording still cancels without installing a fit.
