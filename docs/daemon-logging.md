# Daemon logging

## Output inventory

The tracking daemon's Rust output originally used `log` in `src/bin/cv1touchd.rs`, a synchronous `writeln!(stderr, ...)` with the `cv1touchd: ` prefix. Its callers are listed below. Frequencies describe the trigger, not a guaranteed upper bound during a fault. The daemon has no other library-level Rust diagnostic sink. `say` in `universe_watch` updates a status string under `universe_following`; it writes no output.

The original binary's direct Rust output was limited to `usage`, affinity validation, `--help`/`--version`, and the `--supervise` wrapper's startup/fatal messages. `supervise.rs` owns the supervisor's output readers and file logging and is a separate process role; it is unchanged. Informational `--help`/`--version` return before tracking starts. Ordinary library `eprintln!` sites belong to calibration CLI debug output, ignored benchmarks/live tests, and the CLI's desktop-notification fallback; none are called by the tracking daemon.

The integration through `0236911` retains landmark recovery, both control listeners with their shared 16-client budget/request lock, worker failure guards, and the single dropout writer. Their daemon notices all use `log!` or the bounded `log` callback. Worker-failure exits use the same fatal drain as other fatal exits. No direct stdout/stderr writes were added to the tracking paths; remaining direct binary output belongs to help/version or the separate supervisor role. The supervisor's deadline, grace and queued-output drain changes are retained without modification.

OpenHMD has no installed logging callback in the original daemon. Its `LOGE/LOGW/LOGI` macros in `src/log.h` do **three stdout stdio operations**, not stderr: prefix, formatted message, `puts`. `LOGLEVEL=2` suppresses `LOGV/LOGD`. Linux explicitly line-buffers that stdout in the daemon; Windows calls `ohmd_cv1touch_unbuffer_log` inside the DLL's own C runtime. Neither prevents a full pipe from blocking.

Other vendored drivers are not compiled into this daemon (`drivers=rift`). The debug-file `fprintf(dev->debug_file, ...)` sites have no file opened/assigned by this build; optional PipeWire metadata is a distinct video/debug transport. System libusb builds with `ENABLE_DEBUG_LOGGING` or `USE_SYSTEM_LOGGING_FACILITY` can bypass the library's log callback. The daemon cannot promise bounded behavior for those externally compiled output paths. No descriptor flags are changed to compensate.

## Bounded sink

`src/bin/cv1touchd/log.rs` owns 256 preallocated 2048-byte ring slots and one normal-priority stderr writer. Each producer formats into a stack buffer, tries one slot lock and one compare/exchange, and either enqueues or increments the loss count. It never waits, spins, allocates a message, performs I/O, or grows storage. The sole consumer releases each occupied slot before marking it free, then writes outside the slot lock. A stalled writer cannot hold a producer's free slot; full queues and competing producers lose lines instead. The first design's shared batch-swap mutex failed the healthy-cadence zero-drop test and was replaced for that reason.

The writer preserves accepted records' enqueue order. Native printf fragments accumulate per thread until newline before enqueueing, keeping their original prefixes and per-thread ordering. Native and Rust daemon lines deliberately share stderr now, so journald and supervisor readers see one ordered stream. Other engine clients without the callback keep their original stdout/stderr behavior for ordinary logs. Oversize diagnostics are marked ` [truncated]`; the existing once-a-minute statistics calculations still allocate their working arrays and summary string, but the logging layer does not allocate on their caller.

After output resumes, the writer reports accumulated discarded lines. On ordinary return, panic unwinding or an explicit fatal exit, the daemon makes a best effort to drain for 200 ms. It never joins a writer stalled in an OS write. The default Rust panic hook is also replaced, because its stderr write could otherwise stall a tracking thread. Standalone help/version and the separate supervisor's own startup diagnostics retain their original streams.

Production builds keep native assertions enabled (`debugoptimized`, `b_ndebug=false`). Native assertion sites use `OHMD_ASSERT` from `ohmd-assert.h`, also exposed through the internal/math headers. An explicit project macro cannot be replaced by a later `<assert.h>` or C++ `<cassert>` include. Its failure function formats the expression, file:line and function into a fixed buffer, enqueues through the same native callback, calls a separately installed fatal drain for at most 200 ms, then aborts without ordinary stdio or worker joins. Windows disables UCRT's additional abort message and crash-report dialog on this fatal path. An engine without a receiver still aborts, without attempting synchronous output; standalone unity harnesses compiled without the adapter retain their CRT assertions and the existing `NDEBUG` policy.

Fatal records use their own stack buffer and discard any unfinished printf fragment. Ordinary completed records reset their TLS length/truncation state before entering the receiver. Per-thread receiver/fatal guards abort immediately and silently on reentry, without calling either callback or the drain again. An assertion inside a receiver or a recursive fatal callback therefore cannot reuse a full TLS buffer or recurse through the receiver.

All five fallible Rust C boundaries run their complete bodies through `catch_unwind`. A caught panic's payload is forgotten (its destructor could panic), then `ohmd_cv1touch_abort` performs the same bounded fatal drain and silent abort. This prevents the Rust runtime's later synchronous “panic in a function that cannot unwind” diagnostic. A panic inside the log/fatal receiver reaches the native reentry guard and aborts immediately.

The fatal handler is **not async-signal-safe**: it formats with `snprintf` and may call Rust synchronization/timing code. No signal handler calls it. The separate Unix interrupt handler only stores an atomic flag; Windows console handlers set atomics/an OS event and use their existing fixed console-close wait. They contain no fallible callback dispatch or logging and do not enter this fatal path.

A sibling daemon test can install the same production logger with `daemon_log::init_with_writer(writer: impl std::io::Write + Send + 'static) -> std::io::Result<daemon_log::Guard>` under `cfg(test)`. Install it once in an isolated subprocess, before its callers start; duplicate injection returns `AlreadyExists`. A writer signals when its first `write` begins and waits on a channel until the test releases it. The original `log(msg: impl AsRef<str>)` free function remains available; `log!` formats directly into the fixed buffer. Production uses `daemon_log::init()` after taking shutdown requests and before opening the engine.

## Offline verification and cost

The full-pipe regression starts the built daemon with an invalid option and a pre-filled blocking stderr pipe, without opening devices or using installed state. It failed against the old helper (still alive after 2 s) and passed with the sink (0.22 s including process startup). The pipe's file-status flags stay unchanged. Injected blocked-writer tests exercise a radio-like caller holding a publication lock, queue overflow with exactly 37 discarded lines and one recovery notice, a contended producer slot, the 200 ms exit-flush budget, and the loss notice appearing on the first successful write after an I/O error, before the remaining backlog. A healthy 1 kHz caller plus native/minute-summary bursts loses no lines; three repeat runs also passed. A multi-producer test checks per-thread order and that accepted lines plus loss notices account for all attempts.

Seven mutations failed their targeted tests: blocking slot acquisition, a removed capacity check, a missing drop increment, a missing native callback installation, an 800 ms flush wait, native formatting forced back to stdio, and loss reporting deferred until the backlog drained. The logger tests passed after restoration. The native adapter also has a hardware-independent test of prefixes, partial-line assembly, libusb forwarding and long-line truncation.

Native-assertion subprocess regressions install the production daemon logger and load a test-only bridge to the real `omath.c` source (its math symbols are hidden in the engine library). A NaN quaternion trips its live assertion: a healthy stderr pipe receives the expression, function and file:line, and a completely full blocking pipe still ends with `SIGABRT` within the test's 2 s bound. The full-pipe test timed out on the old code, passed with the fix, failed again when `OHMD_ASSERT` was mutated to plain `assert`, then passed restored. The pipe's blocking flags stay unchanged. Native C++ subprocess tests check header/include ordering, single expression evaluation and abort behavior with the callback and in a standalone build.

Worker-failure subprocess tests install the production logger with a briefly delayed stderr writer. The engine/radio failure reason must reach a healthy pipe before exit, and a completely full blocking pipe must not keep either failure alive beyond 2 s. The healthy-output test failed with the direct process exit inherited during integration, then passed with the bounded fatal drain; the delayed writer makes a missing drain observable regardless of which thread starts writing first.

Callback-panic subprocess tests compile the actual frame/image/report C-boundary source with the daemon's real logger and panic hook. A poisoned-mutex unwrap must abort within 2 s with a full stderr pipe; with a healthy pipe its panic reaches the sink without a non-unwinding-ABI diagnostic. All three full-pipe cases timed out before the catch was added. Native subprocess cases exercise an asserting receiver on short/truncated records, a recursive fatal callback and a pending partial fragment; the truncated baseline also emitted fatal AddressSanitizer diagnostics.

Six further mutations failed: removing the receiver guard, removing the fatal guard, reusing TLS for a fatal record, and removing the frame, image or report catch individually. The native mutations were checked with AddressSanitizer; the restored native and Rust cases passed. The sanitizer run compiles `tests/test_native_log_reentry.c` (which includes the actual adapter) with `-fsanitize=address -fno-omit-frame-pointer`, the same logging defines/include path as its Meson target, and libusb's pkg-config flags, then runs `tests/check_native_log_reentry.py` against it. All four restored native cases abort without sanitizer diagnostics.

On an Intel Core i9-14900KS, Linux x86_64, the optimized Rust test profile (`opt-level=2`) at nice 19 measured 10,000 calls formatting `left: radio back after 0.50 s`. Stderr went to the null device; the synchronous baseline ran before the new writer was started, and queue flushes between 100-call batches were outside the measured intervals. Median/p99 caller time was **465/563 ns before**, **353/3501 ns after**, including the global lookup used by the radio call. The new median was 112 ns lower; the measured new p99 was 0.35% of a 1 ms sample interval. This is wall-clock microbenchmark evidence under concurrent machine load, not a hardware tracking or real-time scheduling measurement, and tail latency includes scheduling noise. No logging work is added to samples that do not emit a diagnostic.

The timing test can be rerun with `cargo test --locked --bin cv1touchd radio_log_cost -- --ignored --nocapture`, with stderr redirected to the null device. Use the project's build-slot wrapper and an isolated build target as for all other checks. The test compares the old synchronous formatting/write path with the production global entry point, fixed-buffer formatting and enqueue path.
