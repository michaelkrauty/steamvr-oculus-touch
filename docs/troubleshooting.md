# Troubleshooting

Start with `cv1touch doctor`, `cv1touch status --json`, and `journalctl --user _COMM=cv1touchd -b`. Include version, distribution, sensor count, build/test results, and the relevant error when reporting a problem. Remove serial numbers, room coordinates, personal paths, and unrelated logs before sharing.

`cv1touch report` puts all of that into one zip file for someone helping you: a summary (version, system, the `doctor` checks, the Oculus USB devices and the drivers they run with, the daemon's status and setup's state), the ends of the daemon's and SteamVR's logs, cv1touch's settings and calibration, and the newest three dropout recordings (below). It names the other files in cv1touch's directories without sending them. On Linux only you can read it; on Windows it takes the permissions of the folder it is saved in (the desktop's are yours alone). The calibration describes where your sensors stand in your room, and SteamVR's log also names your other VR devices, your user folder and your network addresses; look inside before sharing it more widely.

| Symptom | Checks and recovery |
| --- | --- |
| A game holds its gun or tool at the wrong angle for your grip and has no setting for it | `cv1touch tilt DEGREES` pitches the controllers' pose as applications see it (positive: forward end up), applied at once and kept across restarts; `cv1touch tilt 0` shows them as tracked again. Tracking itself is unchanged. |
| Setup reports unknown stages | Existing camera/gravity/render/registration files lack setup-journal evidence. Visually verify the relevant tracking and deliberately adopt them, retaining the files, or recapture. File validity alone is not an accuracy check. |
| Setup reports stale or blocked stages | Run `cv1touch setup --check` for the reason. Resolve device/daemon/SteamVR prerequisites or repeat the affected calibration. Full camera-world replacement invalidates dependent gravity and registration evidence; unrelated valid input settings remain reusable. |
| Setup cannot capture from a script | Captures require an interactive terminal. Use `cv1touch setup --check --json` for read-only automation and run captures interactively. |
| Daemon not reachable | Check `systemctl --user status cv1touchd`; for manual runs check the runtime directory and socket permissions. Only one daemon may run per user. |
| No controllers | Wake them with a button, check batteries, and confirm they are paired to the connected CV1 headset. Headset USB and hidraw access are both required. |
| The log says `controller radio calibration:` (or `controller cache calibration:`) with a reason and `retrying in N s` | The controller's saved factory calibration could not be used, so it is read from the controller again. Reading is retried 1 s after each attempt finishes, then 2 s, 4 s and so on up to 60 s; sleeping and waking do not erase that history, and only a successful read or a different factory calibration resets it. A different controller paired onto that hand is noticed at the next scheduled retry, so it may wait up to 60 s before that read starts. A temporary out-of-memory error retries the saved file instead of treating it as damaged. A read in progress continues even when that controller sends nothing. A radio request that goes unanswered for 5 s is given up and the read is retried after the same delay; the radio is used again once that old request has finished, so the other hand and haptics can wait until then (see below). |
| A calibrated sensor is missing or sends no video | `doctor`'s `sensor_streams` check compares the active calibration with up to four frame-counter samples a second apart and the system's USB list. An unplugged camera says to check its USB cable. A connected camera sending no video may have run out of USB bandwidth: try a different USB controller, not just another socket on the same hub, restart the daemon after moving or reconnecting it (see below), and check kernel USB errors and daemon logs. USB access or the camera's driver can also prevent video. On Windows, `cv1touch sensors` checks the WinUSB driver. The status board shows the same check; `status --json` exposes the counters, `calibrated_sensors` and `ignored_sensors`. Older daemons do not publish their ignore list. |
| New sensor missing or unplaced | Restart after attachment; compare `sensor_total` with the expected count and inspect USB open/start errors. If its frames advance but `placed` is zero, [calibrate the added sensor](setup.md#add-or-remove-sensors). |
| Camera backlog grows or frames are discarded | Inspect changes in `camera_queue` while both controllers are awake and moving. `dropped_frames` counts callback-queue evictions; `pending_frames_dropped` counts deferred frame copies per hand and can rise normally for idle or sleeping controllers awaiting IMU samples. If drops persist during motion, check active-hand tracking, IMU/radio timing, and CPU load. Check USB errors if sensor frame counters stop. |
| A sensor was bumped or moved | Nothing to do while two or more sensors stayed put: the daemon's log says `sensor X ... it moved; placing it again`, then `placed again from the other sensors`, and `cv1touch doctor`'s `sensor_poses` check follows along. Move the controllers where that sensor sees them, for about a minute. A sensor judged moved by mistake is let go again without a change: after 30 s without a labelled sighting of a controller, after 3 minutes without a pose, or when the pose placed is where it was calibrated (the log says why, and `status --json` shows the sensor's `pose` as `released`). If doctor says a sensor could not be placed, that it was placed three times in half an hour, or that fewer than two sensors agree, run `cv1touch setup`. |
| A controller freezes in place mid-game, then carries on or drops out | Its radio reports stopped: the daemon log says `radio silent (in use)` or `(still)`, then `radio back after N s`, or `radio silent for 10 s: standby` if they never came back. An engine reopen holds it the same way, with the same deadline from its last sample; reopening again does not extend it, and stopping the daemon disconnects it immediately. The log says `tracking engine reopening` instead, then `back after N s (engine reopened)`, or `tracking thread stalled` when a thread of the daemon's own fell behind; neither is a dropout, and neither saves a recording. The log gives the elapsed time, including the wait for the radio thread, as `engine reopened after N s`. The native engine reopen took 6.6–6.9 s on one five-sensor setup; the full interval also includes radio teardown and the remaining initialization. Through such a gap the controller stays connected, out of range, where it was, with every button, the trigger and grip held as they were, for up to 10 s, so a game keeps what the hand held; `cv1touch status` shows it as held. Only the daemon's own notices distinguish these causes: during an engine reopen, `cv1touch status` and SteamVR's log still say `radio silent: held as it was`. Cause-specific status and driver wording need the shared-memory flag follow-up. One that never comes back is woken with a button. When it went silent in use, the daemon saves what the radio delivered from 20 s before to 10 s after, with the haptic commands sent meanwhile, as `dropout-<time>-<hand>.rec` in the state directory (the newest ten are kept; `cv1touch report` sends the newest three); a gap of half a second or more that ends is recorded the same way, whether the controller was in use or not, and a shorter one that ends is a blip, not recorded. |
| Rotation works, position is lost | Check sensor views, optical occlusion, calibration, and overlapping coverage. Rotation-only output is not a valid position fix. |
| Controllers translated/rotated from the headset space | `cv1touch universe` says which base station SteamVR tracks the headset from and whether a headset registration measured that station; one placed only by SteamVR's layouts can be centimetres off until more layouts are known. Repeat headset registration after checking gravity levelling and headset tracking. |
| Rendered controller is offset despite good tracking | Run `fit-render` with a recording containing both factory LED models, then reload alignment. Check that native SteamVR contains the CV1 models. |
| Buttons visible locally but unavailable to an app | SteamVR focus and action bindings matter. Run a focused scene app/game and check its Oculus Touch bindings; an inactive action is not proof that a physical button was lost. |
| Grip/trigger does not fully depress, or a stick does not center/reach its edge | Run `cv1touch calibrate inputs`, then `input-test` in a focused VR app. Factory endpoints can shift as hardware changes; [input calibration](input-calibration.md) measures the actual endpoints and offers reset/expert controls. |
| Haptics unavailable | Check the controller is awake/connected, the driver is loaded, and the game's haptic binding is active. |
| Controllers move, but haptics or base-station reports fail inside Steam's Linux container | Install the daemon and SteamVR driver from the same current build, then restart them. The container hides the usual control socket; current builds also use a private socket beside the shared-memory poses. `cv1touch universe-watch` with no argument queries the daemon: with visible base stations it should report fresh driver updates, rather than a once-a-minute SteamVR connection. |
| Real-time scheduling denied | The daemon falls back to normal scheduling. Use the reported reason to diagnose rtkit/session policy; normal scheduling remains supported. No permissive polkit rule is required by this project. |
| Custom Steam library not found | Set `CV1TOUCH_STEAMVR` to the actual runtime directory and `CV1TOUCH_STEAM_ROOT` for its Steam config root. Flatpak/sandboxed Steam is not validated. |

Factory calibration is read from the controller in many small radio requests. Each request gets 5 s to be answered, and every block that arrives restarts that wait, so a complete download can take several seconds. Before giving up on a request, the driver checks once more whether it has finished, so a request that completed while the driver was stalled is not dropped. When a request is given up on (or a vibration request's status cannot be read), the driver reads and throws away the radio's old reply before it sends anything else, then sends each replacement once. The radio has no way to cancel a request: if it never finishes the old one, calibration and vibration wait until it does or until the headset is reopened (restart `cv1touchd`). While waiting for an old reply, checks are spaced at least 100 ms apart across both controllers and vibration, instead of polling for every controller report. After 10 s still waiting, the log says once that the radio is finishing an earlier request and controllers cannot load until it does. Once that request finishes, the next check can take up to 100 ms. A single call to the headset's USB connection can still block for a while. A different controller paired onto a failing hand is detected at its next scheduled retry, up to 60 s later.

Factory data is rejected before it is used when its root is missing; a stick, trigger or grip range endpoint is missing, not a whole number or out of range, or the endpoints are reversed or not strictly increasing; a touch-sensing list has fewer than 8 entries, an unusable value in a slot that is used, or a touch value equal to its resting value; or its IMU or LED data is unusable. Missing dead zones disable their clamp; missing IMU offsets default to zero with one warning per hand and controller; touch-sensing slots 4–6 are ignored. A single failed attempt is retried quietly, as one missed answer on wake-up is normal. Repeated failures warn on the second attempt and then only when the failure changes. Failure messages name the hand, whether the data came from the cache or the radio, what was wrong and how long until the next try, without printing calibration JSON. If this keeps happening, run `cv1touch report` and attach the file it writes to your bug report.

The setup guide retains completion evidence and recording paths in `$XDG_STATE_HOME/cv1touch/setup.json`. Keep it private along with calibration files and recordings; deleting it removes reuse evidence, not calibration. `cv1touch setup --check` is read-only and does not replace physical verification.

Steam's pressure-vessel container supplies the libraries SteamVR needs on Linux. It shares `/dev/shm`, where cv1touch publishes poses, but hides arbitrary sockets in `$XDG_RUNTIME_DIR`. The daemon keeps its usual socket for older drivers and local commands and also listens at `/dev/shm/cv1touch-control-<uid>/control.sock`. The directory must be a real directory owned by the daemon's user with permissions `0700`; the socket is `0600`. If that directory is unsafe or the second socket cannot be opened, the daemon logs one reason and keeps the usual socket. It does not change an existing directory's permissions or ownership. Starting the daemon with `--runtime-dir` or `--shm-name` disables this shared socket, even when the supplied value matches the default, so a separate instance receives commands only through its own endpoint. An older daemon or driver can still work outside the container, but both need the update inside it. This does not validate Steam packaged inside an additional Flatpak or Snap sandbox.

The video check skips when the daemon is unavailable or no calibrated sensors are enabled, with the reason. An engine that is starting or reloading stays checking during sampling. If required camera video still cannot be checked at the end, doctor and report mark it as not verified and fail the check. Check the headset's USB connection and power, then look for an engine open error in the daemon log. On Linux, read it with `journalctl --user _COMM=cv1touchd -n 80`; on Windows, the log is `%LOCALAPPDATA%\cv1touch\state\logs\cv1touchd.log`.

The check does not require awake controllers or optical pose fixes. Sensors excluded with the daemon's repeatable `--ignore-sensor SERIAL` option are left out; extra connected sensors are named as uncalibrated without failing the check. Doctor and report take up to four snapshots, with a one-second wait between them. Elapsed time also includes daemon requests (each with a five-second timeout), the system's USB listing, and reading the fallback calibration for an older daemon. A camera that has just appeared or whose counter restarted stays unverified until a later sample shows frames advancing. The live status board shows this as checking unless another sensor has a confirmed failure; that failure stays visible while pending cameras keep being sampled. A stalled daemon counter alone does not prove a camera is connected: if the system's USB listing fails, the check reports that error and asks you to check the cable, USB access and daemon logs. A camera whose counter still has not advanced after those samples remains unverified. The check fails if any required camera failed or could not be verified. A passing video check does not verify sensor placement or tracking accuracy. The expected sensor list comes from the daemon's active calibration (`calibrated_sensors` in `status --json`, `null` when none is loaded), including a file selected with `--calibration` or `calibration load`. With an older daemon that omits that field, the check explicitly falls back to the default calibration file, which may differ from the file that daemon loaded. Serial comparisons ignore letter case. Video uses an explicit per-sensor format: raw cameras need advancing 64-bit `frames_received`, and JPEG cameras need advancing `frames_decoded`. USB2 CV1 sensors use JPEG in production, including setup and calibration; USB3 uses raw. Received counts advance after defensive raw validation and before any analysis lock or queue; decoded counts advance only after successful JPEG decoding and exact GRAY8 layout validation. Raw `frames_decoded` is `null`. Encoded JPEG payloads can arrive while decoding fails or analysis is delayed; check daemon logs rather than treating this as proven bandwidth loss. A missing/unknown `video_format`, or an unavailable required counter, is not verified. Any decrease or raw/JPEG change starts a fresh sample. `sensor_frames_received: true` and `sensor_video_quality: true` advertise their respective capabilities even with no sensors. Existing `frames` still counts released analysis buffers for compatibility and setup readiness. Board rates say received, decoded, or legacy payload/released buffers; unavailable modern video displays `--`.

`sensors[].frames_dropped` counts rejected image candidates, separate from recording and queue drops. It is `null` when unavailable, not a fabricated zero. Between comparable samples a second apart, three or more rejected images produce a warning with the count; fewer are informational. Advancing video still passes, and a warning does not hide another camera's failure. Rejections observed in an earlier interval remain visible when another camera needs more samples; the warning threshold applies to each interval separately. Check the USB cable, available bandwidth and daemon logs if counts keep rising. Counters reset with a new native device context; a reset or format change is not a burst of dropped images. JPEG rejection is partial: libjpeg can accept some damaged entropy without reporting a warning.

If the daemon does not provide received-frame counters, the check says "video not verified: the daemon is older than this cv1touch". Doctor and report fail this check; the live board marks it as not verified, without blaming a sensor. Restart the daemon after upgrading, as described in [setup's Upgrade section](setup.md#upgrade). On Linux, use `systemctl --user restart cv1touchd`; on Windows, choose **Stop cv1touch**, then **Start cv1touch** in the Start menu. An unavailable acquisition counter is `null`, not zero, and remains unverified for that camera. The other cameras are still checked: a missing camera or another confirmed failure stays visible even when a camera has no counter.

After reconnecting a sensor or moving it to a different USB controller, restart the daemon so it opens the sensor again: on Linux, `systemctl --user restart cv1touchd`; on Windows, choose **Stop cv1touch**, then **Start cv1touch** in the Start menu.

A Linux start attempt that leaves caller errno at `ENOSPC` after libusb returns, whether it failed while selecting the alternate setting or submitting a video transfer, is described as "most likely not enough USB bandwidth on this controller". This is qualified because libusb's own logging can change the error number before it returns. Other startup errors include their codes and advice to check USB access and daemon logs. `status --json` adds `sensor_streams`, keyed by `serial`, including attempts whose sensor object was freed. Each record has `scope: "last_start_attempt"`: `error_kind` is `none`, `likely_usb_bandwidth`, or `other`; `error_code` is the raw start/libusb result; `os_error` is the caller's Linux error number after return (zero if unavailable, and possibly changed by library logging). `alt_setting` is the setting that attempt used if it succeeded, or `null` if it failed. These are historical start results: a successful attempt replaces an earlier failure, but a record can remain after unplugging until detach is reported or the engine closes. Current presence and video are checked separately. An unplugged camera is reported as missing even if the engine retains counters or a successful start; if USB presence cannot be checked, doctor/status/report label a retained error as from the last start attempt. A daemon that reports received counters but omits this startup list still gets counter checks and possible causes. The controller/driver shared-memory ABI is unchanged.

Configuration is under `$XDG_CONFIG_HOME/cv1touch` (default `~/.config/cv1touch`); recordings and learned IMU state are under `$XDG_STATE_HOME/cv1touch` (default `~/.local/state/cv1touch`). Do not copy another user's camera calibration: it encodes their room. Camera/alignment writes preserve timestamped backups; input calibration is replaced atomically and rolls back if live application fails. Raw recordings can contain camera imagery if `--frames` was used; inspect them before sharing.

If a calibration solver fails, read its rejection reason and capture the missing views or orientations. `--force` bypasses acceptance checks and can install unsuitable results; it is an expert diagnostic option, not part of normal setup.
